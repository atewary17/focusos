## 1. Product summary

**FocusOS** helps students overcome procrastination by:

1. Planning the day (subjects → topics → tasks in time slots).
2. Starting short focus sessions that grow over time (10 → 20 → 25 min).
3. Asking "Are you focused?" every 20/30 minutes on phone and watch.
4. Tracking what actually happened (phone apps, laptop apps/sites, watch body data).
5. Showing planned vs actual, distraction patterns, and personal correlations.

**Core idea:** procrastination is a *starting* problem. The app optimises for
starting a session in one tap, and for honest data about the gap between plan
and reality.

**Beta:** 2 users (owner + 1 friend), both on **Android**, laptops with
ActivityWatch, owner has a **CMF Watch Pro 2**.

**Non-goals for the beta:** iOS, app/website blocking, gamification, themes,
public sign-up, paid features, "brain focus" claims from watch data.

### Local development notes (owner's Mac)

- Apple M1, but Ruby 3.3.5 (rbenv) is an x86_64 build running under Rosetta.
  The x86 Tailwind v4 binary crashes under Rosetta (SIGILL), so `~/.zshrc` sets
  `TAILWINDCSS_INSTALL_DIR` to a native arm64 Tailwind binary. If Tailwind is
  upgraded, download the matching arm64 binary or move to a native arm64 Ruby.
- `Procfile.dev` runs `tailwindcss:watch[always]`; without `[always]` the
  Tailwind v4 watcher exits under foreman and stops `bin/dev`.
- Railway builds on Linux from the Dockerfile and is not affected by either.
- `bin/docker-entrypoint` prints the Railway service, environment and commit at
  boot, and stops with the names of any missing required variables.

## 4. Engineering rules (also in CLAUDE.md)

1. **Every record belongs to a user.** Load via `Current.user.<association>`. Every
   new resource gets a test proving user A cannot read/update user B's record (404).
2. **Time:** use `Time.zone.now`, `Date.current`; never `Time.now`/`Date.today`.
   A user's "day" is computed in their zone.
3. **Tests with every change**: model tests for logic, integration tests per action,
   job tests with `travel_to` for anything scheduled.
4. **No new gems without asking.** Candidates already expected (ask first):
   `web-push` (Phase 2), `chartkick` (dashboard). Prefer plain Rails/Stimulus.
5. **Small PRs:** one milestone per branch `m<id>-short-name`; plan → approve → build → test → commit.
6. **Migrations:** reversible, `null: false` where sensible, foreign keys, indexes on `user_id` + date columns.
7. **Privacy:** never log raw usage/health payloads; `dependent: :destroy` on every `has_many` from `User`;
   account deletion must remove everything.
8. **UI:** mobile-first, simple. Today page = one primary action. Tailwind utility classes,
   helpers in `ApplicationHelper` (`input_classes`, `primary_button_classes`, …).
9. **Honest metrics:** no invented "productivity scores". Every number shown is explainable.
10. **Don't let the build become the procrastination:** finish milestones, use them, then continue.

## 6A. Android collector node – full specification

### Purpose
A background app on each beta user's phone that reads **phone usage** (the same
data Digital Wellbeing shows) and **watch data** (via Health Connect) and uploads
it hourly to Rails. Rails stores and analyses; the app does no analysis.

```
CMF Watch ─BT─▶ Nothing X ─writes─▶ Health Connect ──┐
                                                     ├─▶ FocusOS app ─HTTPS hourly─▶ /api/v1 ─▶ Postgres
App use ─recorded by Android─▶ UsageStatsManager ────┘
```

### Facts and limits (design around these)
- **Digital Wellbeing has no API.** Its data comes from Android usage stats, read via
  `UsageStatsManager` with the special **Usage access** permission
  (`android.permission.PACKAGE_USAGE_STATS`, granted by the user in system settings,
  checked with `AppOpsManager.OPSTR_GET_USAGE_STATS`).
- Usage is **per app**, not per screen: Instagram time includes DMs; YouTube includes
  lectures. Reels/Shorts separation (accessibility service) is **out of scope**.
- Android keeps detailed usage **events only for a few days**: sync at least daily,
  and keep a local cursor so nothing is missed.
- The CMF watch writes **heart rate, sleep (+stages), SpO₂, steps** to Health Connect
  (source package `com.nothing.smartcenter`). **No stress, no HRV** from this watch.
  Read HRV anyway if present (other watches).
- Health Connect: Android 14+ built in; Android 9–13 needs the Health Connect app.
  By default a new app can read only ~30 days before the permission was granted.
- Health Connect requires a **permissions-rationale / privacy screen** declared in the
  manifest (`androidx.health.ACTION_SHOW_PERMISSIONS_RATIONALE` activity for ≤13 and a
  `VIEW_PERMISSION_USAGE` activity-alias with category `HEALTH_PERMISSIONS` for 14+),
  plus `<queries><package android:name="com.google.android.apps.healthdata"/></queries>`.
- Background Health Connect reads may need the background-read permission on newer
  versions; if unavailable, read when the app/worker runs in the foreground (sync on app open).
- OEM battery savers can delay `WorkManager`; onboarding asks for battery-optimisation exemption.

### Android tech stack
| Concern | Choice |
| --- | --- |
| Language/UI | Kotlin, Jetpack Compose, Material 3 |
| SDK | minSdk 28, target/compile latest stable (Health Connect client needs compileSdk 36) |
| Networking | Retrofit + OkHttp + kotlinx.serialization (or Moshi) |
| Storage | DataStore (token, cursors, settings); EncryptedSharedPreferences or Keystore-wrapped token |
| Background | WorkManager `PeriodicWorkRequest` (1 h, network constraint) + one-off "Sync now" |
| Health | `androidx.health.connect:connect-client` |
| DI | Manual (small app) or Hilt |
| Build/CI | Gradle Kotlin DSL; GitHub Actions builds a signed release APK |
| Repo | separate repo `focusos-android` (own `CLAUDE.md`) |

### App screens
1. **Sign in** – server URL (prefilled with production), email, password → token
2. **Setup checklist** – each item shows ✓ / ✗ with a "Fix" button:
   Usage access · Health Connect permissions · Battery optimisation exemption · Notifications
3. **Status** – last successful sync, next scheduled sync, records sent today by type,
   last error, "Sync now", "Sign out"
4. **Privacy** – plain-language list of what's collected (also used as the Health Connect rationale screen)

### What is collected
| Data | API | Upload granularity |
| --- | --- | --- |
| Per-app daily totals | `UsageStatsManager.queryAndAggregateUsageStats` / `queryUsageStats(INTERVAL_DAILY)` | one row per app per local day (today re-sent each sync) |
| App sessions | `queryEvents`: `ACTIVITY_RESUMED` → `ACTIVITY_PAUSED/STOPPED` per package | one row per session ≥ 5 s |
| Screen events | `queryEvents`: `SCREEN_INTERACTIVE`, `SCREEN_NON_INTERACTIVE`, `KEYGUARD_HIDDEN` (unlock) | one row per event |
| App labels | `PackageManager.getApplicationLabel` | sent with daily totals |
| Heart rate | `HeartRateRecord` samples | one sample per reading |
| Sleep | `SleepSessionRecord` + stages | one session per night/nap |
| SpO₂ | `OxygenSaturationRecord` | one per reading |
| Steps | `StepsRecord` | intervals as stored |
| HRV (if any) | `HeartRateVariabilityRmssdRecord` | one per reading |

Exclude FocusOS itself and launcher/system UI packages from sessions (keep in daily totals).

### Sync algorithm (per run)
1. Check token and permissions; record permission state for the status call.
2. **Usage:** from `usage_cursor` (default: 7 days ago) to now → build daily totals for each
   affected local date, sessions, screen events → upload in batches of ≤ 500 items.
3. **Health:** for each type, from its cursor (default: 30 days ago) → read pages → upload.
4. Advance each cursor **only after** the server confirms the batch (HTTP 200/201).
5. `POST /api/v1/devices/heartbeat` with app version, permissions and a summary.
6. On failure: exponential backoff (WorkManager), keep cursors, show the error on Status.

All uploads are **idempotent**: re-sending the same data updates rather than duplicates.

### Rails ingest API (C1)

Auth: `Authorization: Bearer <token>`. JSON. Timestamps ISO 8601 UTC. `date` is the
phone's local date. Max body 1 MB. Rate limit 60 requests/hour/device.

```http
POST /api/v1/devices/heartbeat
{ "app_version": "0.1.0", "permissions": { "usage_access": true,
  "health_connect": ["heart_rate","sleep","spo2","steps"], "battery_exempt": false },
  "summary": { "app_usage_days": 120, "app_sessions": 64, "health_samples": 310 } }
→ 200 { "server_time": "…", "min_app_version": "0.1.0" }
```

**Errors:** `{ "error": { "code": "invalid_token" | "validation_failed" | "rate_limited", "message": "…", "details": [...] } }`
with 401 / 422 / 429. A batch with some invalid items returns 422 listing item indexes; valid
items in the same batch are **not** saved (all-or-nothing per request, in a transaction).

**Rails implementation notes**
- `Api::V1::BaseController < ActionController::API` with `TokenAuthentication` concern;
  sets `Current.user` and `Current.device`; never uses cookie sessions.
- Bulk upsert with `upsert_all(..., unique_by: ...)`, scoped to `Current.user`/`Current.device`.
- Validate `kind` values, numeric ranges (HR 25–250, SpO₂ 70–100), timestamps not in the future (+5 min tolerance).
- Settings page: list devices and tokens, revoke a device (deletes its tokens).
- **"Phone data" page** (`/phone`): today and last 7 days of minutes for Instagram, YouTube
  and top 10 apps, pickups, last sync time and permission status per device. Read-only, simple table.
- Account deletion removes devices, tokens and all collected data.

## 7. Notification & check-in design

- **Channels:** Phase 2 web push/ntfy → Phase 3 FCM (primary). Watch receives mirrored phone notifications; answering happens on the phone.
- **Defaults:** active 09:00–21:00 local, interval 25 min, daily cap 20, min gap 5 min.
- **Only nudge when useful:** during a running session or planned block (check-in), when no session started by first anchor + 30 min, at session/break end.
- **Quiet mode:** "Pause 1 hour" and "Done for today" one-tap actions.
- **Message tone:** short, neutral, never shaming. Examples:
  - "Are you focused on {subject}?" [Focused] [Drifting] [Break]
  - "Your {minutes}-minute session is ready. Start now?"
  - "Break's over. One more session?"
- **Log everything** in `notifications` and `check_ins` so we can measure which nudges help.

## 8. API conventions (Phase 3+)

- Full collector endpoint spec: section 6A (authoritative). Every endpoint is documented with a `curl` example in `docs/api.md`
- Base path `/api/v1`, JSON only, `Authorization: Bearer <token>`
- Tokens stored as SHA-256 digests; shown once at creation; revocable in Settings
- Timestamps ISO 8601 UTC; dates as `YYYY-MM-DD` in the user's zone
- Upload endpoints are idempotent (natural unique keys + upsert)
- Errors: `{ "error": { "code": "...", "message": "..." } }` with proper HTTP status
- Rate limit uploads per device; reject payloads > 1 MB

## 11. Risks to watch

| Risk | Mitigation |
| --- | --- |
| Building becomes the procrastination | Gates between phases; use each milestone before starting the next |
| Notifications get muted as noise | Daily cap, state-aware triggers, quiet mode, review logs weekly |
| Android kills background work | WorkManager, battery-optimisation exemption onboarding, server-driven push |
| Usage events expire on the phone before upload | Sync at least daily, cursors advance only after server confirms, status screen shows last sync |
| Health Connect permission dialog fails to open | Rationale activity + `VIEW_PERMISSION_USAGE` alias + `<queries>` in the manifest |
| Instagram/YouTube time is app-level only | Say so in the UI; don't claim Reels/Shorts precision |
| CMF watch misses notifications | Phone is the primary channel; watch is a bonus |
| Health data misinterpreted | Label as body context; explain each indicator; no focus claims |
| Railway cost creep | Check usage weekly; prune raw events after 90 days |
| Privacy of friend's data | Consent, delete-all, no raw payload logging, invite-only sign-up |
