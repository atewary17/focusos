## 1. Product summary

**FocusOS** helps students overcome procrastination by:

1. Planning the day (subjects → topics → tasks in time slots).
2. Starting short focus sessions that grow over time (10 → 20 → 25 min).
3. Asking "Are you focused?" every 20/30 minutes on phone and watch.
4. Tracking what actually happened (phone apps, laptop apps/sites, watch body data).
5. Showing planned vs actual, distraction patterns, and personal correlations.

**Core idea:** procrastination is a *starting* problem. The app optimises for
starting a session in one tap, and for honest data about the gap between plan
and reality.

**Beta:** 2 users (owner + 1 friend), both on **Android**, laptops with
ActivityWatch, owner has a **CMF Watch Pro 2**.

**Non-goals for the beta:** iOS, app/website blocking, gamification, themes,
public sign-up, paid features, "brain focus" claims from watch data.

## 2. Key decisions already made

| Area | Decision |
| --- | --- |
| Backend + web | Rails 8.1, Ruby 3.3, PostgreSQL, Hotwire, Tailwind v4, importmap |
| Auth (web) | Rails built-in authentication + custom sign-up with invite code |
| Jobs | Solid Queue in the primary DB, run inside Puma (`SOLID_QUEUE_IN_PUMA=true`) |
| Cache / cable | In-memory cache, async Action Cable (single service is enough) |
| Hosting | Railway (Dockerfile build, one Postgres service). Dashboard settings, no `railway.toml` |
| Mobile | Native **Kotlin** Android app (Jetpack Compose) in Phase 3 |
| Phone usage data | `UsageStatsManager` in our Android app (Digital Wellbeing has **no API**) |
| Laptop data | ActivityWatch per user + small sync script pushing to our API |
| Watch data | Android **Health Connect** (CMF/Nothing X writes HR, sleep, SpO₂, steps). No HRV, no stress via Health Connect |
| Push to phone/watch | Phase 2: web push / ntfy. Phase 3+: Firebase Cloud Messaging; CMF watch mirrors phone notifications |
| Focus measurement | Check-in answers + distraction time in planned blocks + session completion. Watch data = "body context" only |
| Time zones | Store UTC; each request runs in the user's IANA zone (`users.time_zone`, default `Asia/Kolkata`) |
| Testing | Minitest + fixtures, RuboCop omakase, Brakeman, GitHub Actions CI |
| Cost target | Railway Hobby (~$5/month). Everything else free |

### Local development notes (owner's Mac)

- Apple M1, but Ruby 3.3.5 (rbenv) is an x86_64 build running under Rosetta.
  The x86 Tailwind v4 binary crashes under Rosetta (SIGILL), so `~/.zshrc` sets
  `TAILWINDCSS_INSTALL_DIR` to a native arm64 Tailwind binary. If Tailwind is
  upgraded, download the matching arm64 binary or move to a native arm64 Ruby.
- `Procfile.dev` runs `tailwindcss:watch[always]`; without `[always]` the
  Tailwind v4 watcher exits under foreman and stops `bin/dev`.
- Railway builds on Linux from the Dockerfile and is not affected by either.

## 4. Engineering rules (also in CLAUDE.md)

1. **Every record belongs to a user.** Load via `Current.user.<association>`. Every
   new resource gets a test proving user A cannot read/update user B's record (404).
2. **Time:** use `Time.zone.now`, `Date.current`; never `Time.now`/`Date.today`.
   A user's "day" is computed in their zone.
3. **Tests with every change**: model tests for logic, integration tests per action,
   job tests with `travel_to` for anything scheduled.
4. **No new gems without asking.** Candidates already expected (ask first):
   `web-push` (Phase 2), `chartkick` (Phase 6). Prefer plain Rails/Stimulus.
5. **Small PRs:** one milestone per branch `m<id>-short-name`; plan → approve → build → test → commit.
6. **Migrations:** reversible, `null: false` where sensible, foreign keys, indexes on `user_id` + date columns.
7. **Privacy:** never log raw usage/health payloads; `dependent: :destroy` on every `has_many` from `User`;
   account deletion must remove everything.
8. **UI:** mobile-first, simple. Today page = one primary action. Tailwind utility classes,
   helpers in `ApplicationHelper` (`input_classes`, `primary_button_classes`, …).
9. **Honest metrics:** no invented "productivity scores". Every number shown is explainable.
10. **Don't let the build become the procrastination:** finish milestones, use them, then continue.

## 6. Milestones with acceptance criteria

Each milestone = one branch + PR. "Done" means: tests pass, RuboCop clean,
Brakeman clean, deployed, and used for at least a day.

### Phase 1 – Planner and checklist (web)

**M1.1 Subjects & topics**
- CRUD for subjects (name, color) and nested topics; reorder by position; archive subject
- Topic status changes; subject page shows topic progress (done / total)
- ✅ Cross-user isolation test; Turbo-powered inline add

**M1.2 Tasks & today checklist**
- Tasks with title, optional topic, priority, due date, planned minutes
- Today page shows today's tasks (due today or planned today), tick to complete (Turbo, no reload)
- Overdue section; "Someday" list for undated tasks
- ✅ Completing a task sets `completed_at`; undo works

**M1.3 Day plan**
- `/plan/:date` page: drag or "add to slot" tasks into time slots; default anchor slots (e.g. 09:30, 14:00, 19:00) editable in Settings
- Plan tomorrow from Today in under 2 minutes
- ✅ Planned minutes total shown; slots render in user's zone

**M1.4 Carry-forward**
- First visit of the day shows yesterday's unfinished planned tasks: Move to today / Reschedule / Drop
- ✅ Nothing moves without user confirmation; `carried_from_id` recorded

**M1.5 Recurring tasks**
- Define recurring tasks (days of week); `GenerateRecurringTasksJob` runs hourly and creates today's tasks once per user per day (idempotent), at the user's local morning
- ✅ Job test with `travel_to` across two time zones

### Phase 2 – Focus and check-ins (web)

**M2.1 Focus timer**
- Start session from Today (one tap) or from a task/plan item; server stores `started_at`; Stimulus timer derives remaining time from server state (survives reload, works across tabs)
- Pause/resume/stop; auto-complete at planned end
- ✅ System or integration test for start → complete; only one running session per user

**M2.2 Check-in after session**
- Two taps: focus rating 1–5 and task outcome done/partial/none; skip allowed
- ✅ Outcome updates task status (done → task done)

**M2.3 Progression ladder**
- Today shows target ("2 × 20 min today"); level promotes after N days meeting target with ≥ completion rate; demotes after 3 missed days, with neutral wording
- ✅ Unit tests for promote/demote rules

**M2.4 Reminder settings & templates**
- Settings page: active hours (default 09:00–21:00), interval (20/25/30), daily cap, days, quiet mode ("Pause for 1h / rest of day")
- Editable message templates with variables
- ✅ Validation + preview of rendered message

**M2.5 Delivery channels**
- Web push (service worker + VAPID keys; ask before adding `web-push` gem) and/or ntfy topic per user
- Notification log; "Send test notification" button in Settings
- ✅ Adapter interface `Nudges::Deliverer#deliver(user, message)` with test double

**M2.6 Nudge engine + "Are you focused?"**
- `NudgeTickJob` every minute: for each user inside active hours, decide one of:
  - `no_start` (no session by first anchor + 30 min)
  - `check_in` (interval elapsed during a running session or planned block)
  - `break_over`, `session_end`
- Respect daily cap, quiet mode, min gap between nudges; never two in 5 minutes
- Check-in notification links to a one-tap answer page (`/check_ins/:id/answer?a=focused`) with signed token
- ✅ Time-travel tests covering a full simulated day for two users in different zones

**Gate:** both users use it daily for 2 weeks; start rate ≥ 80% before Phase 3.

### Phase 3 – Android app (Kotlin) + API

**M3.1 Rails API v1**
- `POST /api/v1/sessions` (email/password → bearer token), `DELETE` to revoke
- `GET /api/v1/today` (plan, next session, ladder target), `POST /api/v1/focus_sessions`, `PATCH .../:id`
- `POST /api/v1/check_ins/:id/answer`, `POST /api/v1/devices`, `POST /api/v1/push_tokens`
- JSON via plain `render json:` or Jbuilder-free serializers (POROs); token auth concern; rate limits
- Full contract: `docs/api.md`
- ✅ Request tests for every endpoint incl. auth failures and cross-user access

**M3.2 Android skeleton**
- Kotlin, Jetpack Compose, Material 3, min SDK 28, Retrofit/Ktor client, DataStore for token, Hilt (or manual DI)
- Screens: Login, Today (next session, Start button, tasks), Session timer
- ✅ Builds signed APK via Gradle; GitHub Actions build job

**M3.3 Push + check-ins (FCM)**
- Firebase project (free); app registers FCM token → API
- Rails sends FCM HTTP v1 messages (service account JSON in Railway variable)
- Notification actions: **Focused / Drifting / Break** → API answer without opening the app
- CMF/Nothing X app set to mirror FocusOS notifications → watch vibrates
- ✅ Manual test checklist on both phones; battery optimisation exemption guide

**M3.4 Phone usage upload**
- `UsageStatsManager` with "Usage access" permission onboarding screen
- WorkManager periodic job (hourly): daily per-app foreground time + launches; optional event intervals
- Upload to `POST /api/v1/app_usage` (idempotent upsert)
- ✅ Handles missing permission, offline, and backfill of last 7 days

**M3.5 Distribution**
- Signed APK on GitHub Releases or Play Console internal testing
- In-app version check

### Phase 4 – Laptop tracking

**M4.1 ActivityWatch sync script**
- Small Python or Ruby script (cron/launchd every 10 min): reads local AW buckets (window, afk, web-chrome) since cursor → `POST /api/v1/activity_events` with API token
- ✅ Idempotent; documented install for Mac (and Windows if friend needs it)

**M4.2 Classification**
- Default categories + rules seeded per user (YouTube, Instagram, Reels, Shorts, VS Code, docs sites…)
- Settings UI to add rules (regex on app/package/domain/title), test a rule, reclassify history
- ✅ Same rules apply to phone packages and laptop events

**M4.3 Distraction during sessions**
- After each session, compute `distraction_seconds` from overlapping distracting phone + laptop activity (excluding AFK)
- Optional "drift" nudge after N distracting minutes during a planned block
- ✅ Overlap calculation unit tests

### Phase 5 – Watch / Health Connect

**M5.1 Health Connect read (Android)**
- Permissions: heart rate, sleep, SpO₂, steps (+ HRV if present)
- Daily sync job uploads samples and sleep sessions → `POST /api/v1/health/*`
- ✅ Diagnostics screen: which data types exist, latest timestamp, source package

**M5.2 Derived indicators (Rails)**
- Sleep duration, sleep midpoint, regularity (std dev of midpoint over 7 days), sleep debt vs 7h
- Wake-to-first-session delay; resting HR (lowest 30-min average overnight) and 7-day trend
- Sedentary streaks during the day; simple readiness indicator (documented formula)
- "Elevated while still": HR > personal baseline + X while steps = 0 (shown as context only)
- ✅ Each indicator has a unit test with synthetic data and a plain-language explanation in the UI

### Phase 6 – Reports and insights

**M6.1 Nightly rollup**
- `DailyStatsRollupJob` per user after local midnight → `daily_stats`
- ✅ Re-runnable for any date range

**M6.2 Daily report**
- Planned vs actual minutes, sessions, check-in focus %, distraction time (phone + laptop), feed apps time, sleep, first start time
- One suggestion based on the biggest gap (rule-based)

**M6.3 Weekly & monthly**
- Best hours (heatmap from check-ins + completed sessions), best days, subject split, week-over-week change
- Correlations: sleep vs focus %, bedtime vs first-start time (show only with ≥ 10 days of data)

**M6.4 Rules engine**
- Built-ins (toggleable): YouTube > 30 min warning; no session by 10 AM; 15 min distraction during plan; 3 sessions → long break; missed task → reschedule suggestion
- Rule = condition (jsonb) + action (jsonb), evaluated by the nudge tick

**M6.5 Optional AI summary**
- Weekly summary text from `daily_stats` via a local model or Claude API with a hard monthly budget. Off by default.

## 7. Notification & check-in design

- **Channels:** Phase 2 web push/ntfy → Phase 3 FCM (primary). Watch receives mirrored phone notifications; answering happens on the phone.
- **Defaults:** active 09:00–21:00 local, interval 25 min, daily cap 20, min gap 5 min.
- **Only nudge when useful:** during a running session or planned block (check-in), when no session started by first anchor + 30 min, at session/break end.
- **Quiet mode:** "Pause 1 hour" and "Done for today" one-tap actions.
- **Message tone:** short, neutral, never shaming. Examples:
  - "Are you focused on {subject}?" [Focused] [Drifting] [Break]
  - "Your {minutes}-minute session is ready. Start now?"
  - "Break's over. One more session?"
- **Log everything** in `notifications` and `check_ins` so we can measure which nudges help.

## 8. API conventions (Phase 3+)

- Base path `/api/v1`, JSON only, `Authorization: Bearer <token>`
- Tokens stored as SHA-256 digests; shown once at creation; revocable in Settings
- Timestamps ISO 8601 UTC; dates as `YYYY-MM-DD` in the user's zone
- Upload endpoints are idempotent (natural unique keys + upsert)
- Errors: `{ "error": { "code": "...", "message": "..." } }` with proper HTTP status
- Rate limit uploads per device; reject payloads > 1 MB
- Endpoint-by-endpoint contract: `docs/api.md`

## 11. Risks to watch

| Risk | Mitigation |
| --- | --- |
| Building becomes the procrastination | Gates between phases; use each milestone before starting the next |
| Notifications get muted as noise | Daily cap, state-aware triggers, quiet mode, review logs weekly |
| Android kills background work | WorkManager, battery-optimisation exemption onboarding, server-driven push |
| CMF watch misses notifications | Phone is the primary channel; watch is a bonus |
| Health data misinterpreted | Label as body context; explain each indicator; no focus claims |
| Railway cost creep | Check usage weekly; prune raw events after 90 days |
| Privacy of friend's data | Consent, delete-all, no raw payload logging, invite-only sign-up |
